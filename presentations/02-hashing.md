# Хеш-функція

**Хеш-функція** — детермінована функція, яка перетворює вхідні дані довільного розміру у вихідне значення фіксованого розміру

**Ключові властивості:**

- **Детермінованість** — однаковий вхід завжди дає однаковий вихід
- **Фіксований розмір** — вихід однакової довжини незалежно від входу
- **Односпрямованість** — неможливо відновити вхідні дані з хешу
- **Лавинний ефект** — зміна 1 біта входу змінює ~50% бітів виходу
- **Стійкість до колізій** — практично неможливо знайти два входи з однаковим хешем

---

# Лавинний ефект (avalanche effect)

```bash
echo -n "Hello" | sha256sum
→ 185f8db32271fe25f561a6fc938b2e264306ec304eda518007d1764826381969

echo -n "hello" | sha256sum
→ 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
```

Одна велика літера `H` замість малої `h` — і результат **повністю інший**

Жодного спільного фрагмента. Неможливо передбачити, як зміниться хеш

---

# SHA-256

**SHA** = Secure Hash Algorithm, **256** = розмір виходу в бітах

32 байти, 64 шістнадцяткових символи

```
┌────────────────┐     ┌──────────────┐     ┌────────────────────┐
│ Вхідні дані    │────→│   SHA-256    │────→│ 256-бітний хеш     │
│ (будь-який     │     │   hash()     │     │ (64 hex символи)   │
│  розмір)       │     └──────────────┘     └────────────────────┘
└────────────────┘
```

Сімейство SHA-2, розроблене NSA, опубліковане NIST (2001)

---

# Практичне застосування SHA-256

- **Перевірка цілісності файлів** (checksums) — `sha256sum file.zip`
- **Git commit hashes** — кожен коміт ідентифікується хешем вмісту
- **Blockchain** — у Bitcoin майнінг = пошук nonce з потрібним хешем
- **Цифрові підписи** — підписується хеш документа, а не весь документ

---

# А що, якщо хешувати паролі?

SHA-256 чудово підходить для перевірки цілісності файлів

А що, якщо використати його для зберігання паролів?

Здавалося б, паролі не у відкритому вигляді — все безпечно...

**Але ні.** Розглянемо, які інструменти є в арсеналі зловмисника

---

# Витік бази даних

Максим Витребенько працює в компанії, яка зберігає паролі як SHA-256 хеші. Базу зламали. Що бачить атакуючий?

| Користувач | SHA-256 хеш пароля |
|---|---|
| maksym.vytrebenko | `5e884898da28...` |
| olena.koval | `ef92b778bafe...` |
| admin | `8c6976e5b541...` |

Атакуючий не бачить самих паролів — лише хеші. Але чи означає це, що паролі у безпеці?

---

# Brute force: швидкість GPU

SHA-256 спроєктована як **швидка** хеш-функція — і це стає проблемою:

| Пристрій | Швидкість SHA-256 |
|---|---|
| CPU (сучасний) | ~50 млн хешів/сек |
| GPU (NVIDIA RTX 4090) | ~10 млрд хешів/сек |
| Спеціалізований ASIC | ~100+ млрд хешів/сек |

Пароль із 6 малих латинських літер: 26^6 = 309 млн комбінацій

```
309,000,000 / 10,000,000,000 = 0.03 секунди
```

**0.03 секунди** — шестисимвольний пароль зламується миттєво

---

# Веселкові таблиці (rainbow tables)

Попередньо обчислені таблиці: хеш → пароль

Замість обчислення на льоту — пошук у готовій базі мільярдів пар

**Приклад:**

`5e884898da28047151d0e56f8dc...` = `password`

Хеш є у кожній веселковій таблиці — одна операція пошуку замість мільярдів обчислень

> SHA-256 — **занадто швидкий** для зберігання паролів. Швидкість стає вразливістю

---

# Сіль (Salt) — перший захист

**Сіль** (salt) — випадкове значення, що додається до пароля перед хешуванням: `hash(salt + password)`

```
Без солі:
"password123" ──→ SHA-256 ──→ ef92b778bafe...
"password123" ──→ SHA-256 ──→ ef92b778bafe...  ← ОДНАКОВІ!

З сіллю:
"a1b2c3" + "password123" ──→ SHA-256 ──→ 7c4f8a91d3e2...
"x9y8z7" + "password123" ──→ SHA-256 ──→ 1f3e5d7c9b0a...  ← РІЗНІ!
```

Однакові паролі — різні хеші. Атакуючий навіть не визначить, що паролі збігаються

---

# Сіль у базі даних

Сіль зберігається поруч із хешем. Сіль — це **не секрет**, а **унікальне значення** для кожного користувача

| Користувач | Сіль | Хеш |
|---|---|---|
| maksym.vytrebenko | `a1b2c3d4` | `7c4f8a91...` |
| olena.koval | `e5f6g7h8` | `2d3e4f5a...` |

**Чому rainbow tables не працюють з сіллю:**

Без солі — одна таблиця для всіх хешів. З сіллю — потрібна **окрема таблиця для кожної солі**. 10 000 користувачів = 10 000 таблиць — нездійсненно

---

# Чому солі недостатньо

- SHA-256 залишається **блискавично швидкою** навіть з сіллю
- Сіль зупиняє rainbow tables, але **не зупиняє brute force**
- Атакуючий перебирає кожен хеш окремо зі швидкістю мільярдів/сек

Нам потрібно щось **повільніше**

---

# Розтягування ключа (key stretching)

**Ідея:** хеш-функція, яка **навмисно повільна**

- Достатньо повільна, щоб brute force став непрактичним
- Достатньо швидка, щоб логін не займав хвилини

Хеш-функція виконує тисячі або мільйони внутрішніх ітерацій, щоб кожне обчислення займало відчутний час

---

# bcrypt (1999)

На основі шифру **Blowfish**, з параметром **cost factor** та **вбудованою сіллю**

Формат виходу:

```
$2b$12$LJ3m4ys3Lg7E90WYOF3O2u8VYClVxcBqRKqhW8MiNAJG6SAPO2nJy
 ^^^  ^^  ^^^^^^^^^^^^^^^^^^^^^^  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  │    │          │                          │
  │    │          │                          └── хеш
  │    │          └── сіль (22 символи, base64)
  │    └── cost factor
  └── версія алгоритму ($2b$)
```

| Cost factor | Ітерацій | Час хешування |
|---|---|---|
| 10 | 1 024 | ~100 мс |
| 12 | 4 096 | ~300 мс |
| 14 | 16 384 | ~1 сек |

---

# bcrypt: приклад

```python
import bcrypt

password = "supersecret".encode('utf-8')
salt = bcrypt.gensalt(rounds=12)
hashed = bcrypt.hashpw(password, salt)

# Перевірка
bcrypt.checkpw(password, hashed)  # True
```

10 млрд SHA-256/сек → ~3 bcrypt/сек

Збільшення cost factor на 1 **подвоює** час обчислення

---

# Argon2 (2015)

Переможець **Password Hashing Competition** (2015)

Три виміри складності:
- **Час** (time cost) — кількість ітерацій
- **Пам'ять** (memory cost) — скільки RAM потрібно для одного хешу
- **Паралелізм** (parallelism) — кількість потоків

Три варіанти:
- **Argon2d** — стійкий до GPU, вразливий до side-channel атак
- **Argon2i** — стійкий до side-channel, менш ефективний проти GPU
- **Argon2id** — гібрид, **рекомендований** для хешування паролів

---

# Чому memory-hardness важлива

```
bcrypt:                         Argon2:
┌──────────┐                    ┌──────────┐
│ Повільний │                    │ Повільний │
│ по часу   │                    │ по часу   │
│           │                    │ + багато  │
│           │                    │   RAM     │
│           │                    │ + потоки  │
└──────────┘                    └──────────┘
GPU: може паралелити          GPU: не вистачає
     тисячі обчислень               пам'яті на ядро
```

64 МБ на хеш x 10 000 ядер GPU = **640 ГБ RAM** — непрактично для атакуючого

---

# Порівняння алгоритмів

| | SHA-256 | bcrypt | Argon2 |
|---|---|---|---|
| Призначення | загальне хешування | хешування паролів | хешування паролів |
| Швидкість | дуже швидкий | повільний (налашт.) | повільний (налашт.) |
| Вбудована сіль | ні | так | так |
| Memory-hard | ні | ні | **так** |
| GPU-стійкість | ні | частково | **так** |
| Рекомендація | файли, підписи | паролі (legacy) | **паролі (стандарт)** |

# CSPRNG vs PRNG

<div class="columns">
<div>

**PRNG** (Pseudo-Random Number Generator)

- Детермінований — знаючи seed, відтворює послідовність
- Передбачуваний
- Для ігор, симуляцій, статистики
- `random.randint()` (Python)
- `Math.random()` (JavaScript)

</div>
<div>

**CSPRNG** (Cryptographically Secure PRNG)

- Неможливо передбачити наступне значення
- Використовує ентропію ОС
- Для токенів, солей, ключів
- `secrets.token_hex()` (Python)
- `os.urandom()` (Python)

</div>
</div>

---

# Практичні правила випадковості

**Правильно** — для токенів, солей, ключів:

```python
import secrets
token = secrets.token_hex(32)
```

```bash
openssl rand -hex 32
```

**Неправильно** — передбачувані, НЕ для безпеки:

- `random.random()` (Python)
- `Math.random()` (JavaScript)
- `rand()` (C/PHP)

Ці функції — PRNG. Знаючи seed, атакуючий відтворить усі значення

---

# Підсумки

- **Хеш-функція** — «цифровий відбиток» даних: одностороння, детермінована, з лавинним ефектом
- **SHA-256** підходить для цілісності, але **занадто швидкий** для паролів
- **Сіль** захищає від rainbow tables, але не від brute force
- **bcrypt** — повільне хешування з cost factor
- **Argon2id** — сучасний стандарт (memory-hard, GPU-стійкий)
- Для криптографії лише **CSPRNG** — ніколи `random()`
