# Навіщо шифрування в OAuth

OAuth працює через **інтернет** — відкриту мережу

Без шифрування:
- Authorization code летить відкритим текстом
- Access token видно кожному маршрутизатору
- Credentials користувача перехоплюються

**OAuth 2.0 вимагає TLS** (RFC 6749, Section 1.6)

> Шифрування = **конфіденційність** (Confidentiality) — третій стовп CIA Triad

---

# Де шифрування в OAuth-системі

```
Client ←──── TLS (AES-GCM) ────→ Authorization Server
  │                                        │
  │          TLS (AES-GCM)                 │
  └──────────────────────────→ Resource Server

Всередині TLS-каналу:
  • JWT tokens — підписані (RS256/ES256)
  • JWE tokens — зашифровані (опціонально)
  • Auth code, credentials — захищені TLS
```

---

# Симетричне шифрування

**Один ключ** для шифрування та розшифрування

```
     Максим                              Сервер
  ┌──────────┐                        ┌──────────┐
  │  Ключ K  │                        │  Ключ K  │
  └────┬─────┘                        └────┬─────┘
       │                                    │
       ▼                                    ▼
  Encrypt(K, "Привіт") → 0x7a3f... → Decrypt(K, 0x7a3f...) = "Привіт"
```

**AES** (Advanced Encryption Standard) — стандарт з 2001 року

| Ключ | Безпека | Використання |
|---|---|---|
| AES-128 | високий | TLS |
| AES-256 | дуже високий | TLS, дискове шифрування |

---

# AES-GCM — сучасний стандарт

**GCM** (Galois/Counter Mode) = шифрування + автентифікація (AEAD)

```
Вхід:                             Вихід:
┌─────────────┐                  ┌──────────────────┐
│ Ключ (256b) │──┐               │ Шифротекст       │
├─────────────┤  ├→ AES-GCM ───→ ├──────────────────┤
│ Nonce (12B) │──┤               │ Auth Tag (16B)   │
├─────────────┤  │               └──────────────────┘
│ Plaintext   │──┘
└─────────────┘
```

- **Конфіденційність** — дані зашифровані
- **Цілісність** — зміна навіть 1 біту → Auth Tag не збігається
- Використовується в **TLS 1.3** (`TLS_AES_256_GCM_SHA384`)

---

# Проблема: як передати ключ?

Симетричне шифрування потребує **спільного ключа**

```
┌──────────┐    Ключ K = ???    ┌──────────┐
│  Максим  │ ──────────────────→│  Сервер  │
│          │   як передати      │          │
│          │   безпечно?        │          │
└──────────┘                    └──────────┘
```

Якщо надіслати ключ відкритим текстом — зловмисник перехопить

**Рішення:** асиметричне шифрування

# Асиметричне шифрування

**Пара ключів:** публічний (відкритий) + приватний (секретний)

```
┌─────────────────────────┐
│       СЕЙФ МАКСИМА      │
│  ┌───────────────────┐  │
│  │ Щілина            │  │ ← будь-хто кидає конверт
│  └───────────────────┘  │
│         🔒              │ ← відкрити може лише Максим
└─────────────────────────┘

Public key  = щілина (відома всім)
Private key = ключ від сейфа (лише у Максима)
```

**Приватний ключ ніколи не передається по мережі.** Публічний — роздається всім (сертифікат, JWKS endpoint).

---

# Гібридне шифрування (TLS)

Асиметричне **повільне** (~1 MB/s) → лише для обміну ключами
Симетричне **швидке** (~1 GB/s) → для шифрування даних

```
1. Server ──── Public Key ────→ Client
   (сертифікат із публічним ключем)

2. Client ──── Encrypt(PubKey, AES_Key) ──→ Server
   (клієнт шифрує випадковий AES-ключ)

3. Client ←── AES-GCM(AES_Key, data) ────→ Server
   (далі все через швидкий AES)
```

---

# Цифрові підписи

Підпис = **автентичність** + **цілісність**

```
Authorization Server:
  JWT payload ──→ Sign(PrivateKey) ──→ JWT з підписом

Resource Server:
  JWT з підписом ──→ Verify(PublicKey) ──→ ✓ або ✗
```

**Ключова властивість для OAuth:**

Resource Server перевіряє підпис за **публічним ключем** — йому НЕ потрібен приватний ключ Authorization Server

---

# Де підписи в OAuth

| Де | Що підписується | Алгоритм |
|---|---|---|
| **JWT access token** | Claims (iss, sub, exp...) | RS256, ES256 |
| **JWT ID token** | Інформація про користувача | RS256, ES256 |
| **TLS сертифікат** | Публічний ключ сервера | RSA, ECDSA |

---

# TLS 1.3 Handshake

```
Client                                    Server
  │                                          │
  │── ClientHello (алгоритми) ──────────────→│
  │                                          │
  │←── ServerHello + Certificate ────────────│
  │                                          │
  │  [Перевірка: сертифікат підписаний       │
  │   довіреним CA? Не expired?]             │
  │                                          │
  │── Key Exchange (ECDH) ──────────────────→│
  │                                          │
  │←──── AES-GCM encrypted data ────────────→│
```

---

# Сертифікати та PKI

Як клієнт знає, що сервер справжній?

```
Root CA (вбудований у браузер)
  └── Intermediate CA
        └── Сертифікат сервера (google.com)
              └── Публічний ключ + підпис від CA
```

Браузер перевіряє **ланцюжок довіри** (certificate chain)

Для OAuth: TLS гарантує, що Authorization Server — справжній Google/GitHub, а не фішинговий сайт

---

# JWS vs JWE

| | JWS (підписаний JWT) | JWE (зашифрований JWT) |
|---|---|---|
| Конфіденційність | **ні** — payload видимий | **так** — зашифрований |
| Цілісність | **так** — підпис | **так** — AEAD |
| Використання | access token, ID token | sensitive claims |

> **Важливо:** стандартний JWT — **не зашифрований!** Payload — base64url, будь-хто може прочитати

---

# Підсумки

- **TLS обов'язковий** для OAuth — без нього токени відкриті
- **AES-GCM** — симетричне шифрування + автентифікація
- **RSA/ECDSA** — асиметричне шифрування та підписи
- **Гібридне** — TLS поєднує обидва підходи
- **JWT підписаний, але не зашифрований** — payload видимий
- **Цифрові підписи** — основа JWT: AS підписує, RS перевіряє
