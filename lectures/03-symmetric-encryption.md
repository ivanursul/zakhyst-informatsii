## 1. Навіщо шифрування в контексті OAuth

### Мотивація

У попередніх лекціях ми розглянули **цілісність** (хешування) та **автентифікацію** (Identity, Authentication, Authorization). Але OAuth працює через інтернет — відкриту мережу, де зловмисник може **перехопити** будь-яке повідомлення. Без шифрування:

- Authorization code летить відкритим текстом
- Access token видно кожному маршрутизатору по дорозі
- Credentials користувача можна перехопити

Шифрування забезпечує **конфіденційність** (Confidentiality) — третій стовп CIA Triad. У контексті OAuth нас цікавить не стільки «як AES перемішує біти», скільки **де і навіщо** використовується шифрування.

### Що бачить зловмисник без TLS

Уявімо, що Максим Витребенько авторизується через OAuth **без шифрування**. Зловмисник у тій самій Wi-Fi мережі запускає сніфер і бачить:

```
GET /authorize?response_type=code&client_id=notes-app&redirect_uri=...  HTTP/1.1
Host: auth.example.com
Cookie: session=abc123

──→ Відповідь:
HTTP/1.1 302 Found
Location: https://notes.example.com/callback?code=SplxlOBeZQQYbYS6WxSbIA

──→ Клієнт обмінює code на token:
POST /token HTTP/1.1
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=SplxlOBeZQQYbYS6WxSbIA
&client_secret=my-secret-123

──→ Відповідь:
{
  "access_token": "eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiJtYWtzeW0i...",
  "token_type": "Bearer"
}
```

Зловмисник отримав:
- **Authorization code** — може обміняти на токен раніше за Максима
- **Client secret** — може видавати себе за додаток
- **Access token** — має повний доступ до ресурсів Максима

З TLS все це зашифроване — зловмисник бачить лише `0x17 0x03 0x03 ...` (TLS Application Data).

### Де шифрування з'являється в OAuth

```
┌──────────────────────────────────────────────────────────────┐
│                    OAuth 2.0 Flow                            │
│                                                              │
│  Client ←──── TLS (AES-GCM) ────→ Authorization Server     │
│    │                                        │                │
│    │          TLS (AES-GCM)                 │                │
│    └──────────────────────────→ Resource Server              │
│                                                              │
│  Всередині TLS-каналу:                                      │
│    • JWT access tokens — підписані (RSA/ECDSA)              │
│    • JWE encrypted tokens — зашифровані (RSA + AES)         │
│    • Authorization code — захищений TLS                      │
│    • Client credentials — захищені TLS                       │
└──────────────────────────────────────────────────────────────┘
```

Ми не будемо заглиблюватись у математику шифрів. Натомість розглянемо їх як **інструменти**, які OAuth використовує для безпеки.

## 2. Симетричне шифрування — AES як чорна скринька

### Ідея

**Симетричне шифрування** — обидві сторони використовують **один і той самий ключ** для шифрування та розшифрування.

```
     Максим                              Сервер
  ┌──────────┐                        ┌──────────┐
  │  Ключ K  │                        │  Ключ K  │
  └────┬─────┘                        └────┬─────┘
       │                                    │
       ▼                                    ▼
  Encrypt(K, "Привіт") ──→ 0x7a3f... ──→ Decrypt(K, 0x7a3f...) = "Привіт"
```

### AES — стандарт

**AES** (Advanced Encryption Standard) — стандарт симетричного шифрування з 2001 року. Використовується скрізь: TLS, дискове шифрування, Wi-Fi, VPN, месенджери.

Що потрібно знати:

| Параметр | Значення |
|---|---|
| Розмір ключа | 128, 192 або 256 бітів |
| Безпека | AES-256 — жодних відомих практичних атак |
| Швидкість | Дуже швидкий, апаратна підтримка в сучасних CPU |

Ви вже використовуєте AES щодня, навіть не замислюючись:

| Де | Як використовується |
|---|---|
| **HTTPS** (кожен сайт) | TLS шифрує трафік через AES-GCM |
| **Wi-Fi (WPA2/WPA3)** | Пароль Wi-Fi → AES-ключ → шифрування пакетів |
| **FileVault / BitLocker** | Весь диск зашифрований AES-256 |
| **WhatsApp / Signal** | End-to-end шифрування повідомлень через AES |
| **ZIP з паролем** | AES-256 шифрування архіву |

### Головна проблема симетричного шифрування

Як безпечно передати ключ K? Якщо Максим Витребенько надішле ключ через інтернет відкритим текстом — зловмисник перехопить його.

```
Проблема "курки та яйця":

Максим хоче надіслати зашифроване повідомлення серверу.
  → Потрібен спільний ключ K.
  → Щоб передати K безпечно, потрібно шифрування.
  → Щоб шифрувати, потрібен ключ.
  → ???
```

Цю проблему вирішує **асиметричне шифрування** (розділ 4) — воно дозволяє безпечно обмінятися симетричним ключем через відкритий канал.

## 3. AES-GCM — що використовує TLS

AES має різні режими роботи. У контексті OAuth важливий лише один — **AES-GCM** (Galois/Counter Mode), який використовується в TLS 1.3.

**AES-GCM** — шифрує та автентифікує одночасно:

- **Конфіденційність** — дані зашифровані (Counter Mode)
- **Цілісність** — якщо хтось змінить шифротекст, це буде виявлено (Authentication Tag)
- Це називається **AEAD** (Authenticated Encryption with Associated Data)

```
Вхід:                                    Вихід:
┌─────────────┐                         ┌──────────────────┐
│ Ключ (256b) │──┐                      │ Шифротекст       │
├─────────────┤  ├──→ AES-GCM ────────→ ├──────────────────┤
│ Nonce (12B) │──┤                      │ Auth Tag (16B)   │
├─────────────┤  │                      └──────────────────┘
│ Plaintext   │──┘
└─────────────┘
```

**Nonce** (Number used once) — 12 байтів випадкових даних. Має бути **унікальним** для кожного шифрування з тим самим ключем. Якщо nonce повторюється — зловмисник може вивести plaintext. Nonce не є секретом — зберігається поруч із шифротекстом.

**Auth Tag** — 16-байтовий тег автентифікації. Якщо зловмисник змінить хоча б один біт шифротексту, Auth Tag не збігатиметься, і розшифрування буде відхилене. Це захищає від атак на підміну даних.

### Навіщо автентифікація разом із шифруванням?

Без автентифікації (тільки шифрування) зловмисник не може прочитати дані, але може **змінити** їх наосліп. Наприклад:

```
Оригінал (зашифрований):   "transfer 100 USD to Alice"
                                     ↓ зловмисник змінює біти
Модифікований шифротекст:  "transfer 900 USD to Alice"
```

З AES-GCM така підміна **неможлива** — Auth Tag виявить будь-яку зміну.

Коли ви бачите `TLS_AES_256_GCM_SHA384` у налаштуваннях HTTPS — це означає: AES з 256-бітним ключем, режим GCM, хеш SHA-384.

Можна побачити це в реальному з'єднанні:

```bash
$ openssl s_client -connect google.com:443 2>/dev/null | grep "Cipher"
New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384
```

## 4. Асиметричне шифрування — публічний і приватний ключі

### Ідея

**Асиметричне шифрування** використовує **пару ключів**: публічний (public key) та приватний (private key). Що зашифровано публічним — розшифровується лише приватним, і навпаки.

```
Аналогія: сейф із щілиною для депозитів

┌─────────────────────────────────┐
│         СЕЙФ МАКСИМА            │
│                                 │
│  ┌───────────────────────────┐  │
│  │  Щілина для конвертів     │  │  ← будь-хто кидає конверт
│  └───────────────────────────┘  │
│                                 │
│  Ключ від сейфа — лише          │  ← відкрити може лише
│  у Максима                      │    Максим
└─────────────────────────────────┘

Public key  = адреса сейфа + щілина (відомі всім)
Private key = ключ від сейфа (лише у Максима)
```

### Приватний ключ ніколи не передається

Це найважливіше правило асиметричного шифрування. Приватний ключ **генерується на сервері і залишається на сервері**. Публічний ключ — навпаки, роздається всім охочим.

```
┌─────────────────────────────────────────────────────────┐
│  Authorization Server                                   │
│                                                         │
│  $ openssl genrsa -out private.pem 2048                │
│  $ openssl rsa -in private.pem -pubout -out public.pem │
│                                                         │
│  private.pem → зберігається тут, НІКОЛИ не надсилається│
│  public.pem  → публікується через JWKS endpoint        │
└─────────────────────────────────────────────────────────┘
                          │
                          ▼ публічний ключ доступний усім
         GET /.well-known/jwks.json
         {
           "keys": [{
             "kty": "RSA",
             "kid": "auth-server-key-1",
             "n": "0vx7agoebGcQ...",   ← публічний ключ
             "e": "AQAB"
           }]
         }
```

Resource Server завантажує публічний ключ з JWKS endpoint і використовує його для перевірки підписів JWT. Приватний ключ для цього **не потрібен**.

### Де використовуються різні алгоритми

| Алгоритм | Для чого | Де в OAuth |
|---|---|---|
| **RSA** | Шифрування, підписи | JWT підпис (RS256), JWE шифрування |
| **ECDSA** | Підписи (компактніші) | JWT підпис (ES256) |
| **Diffie-Hellman / ECDH** | Обмін ключами | TLS handshake |

Математичні деталі нам не потрібні. Важливо розуміти **принцип**: публічний ключ — відкритий для всіх, приватний — тільки у власника.

### Гібридне шифрування

Чому не шифрувати все асиметрично? Тому що це **дуже повільно**:

| Операція | Швидкість (приблизно) |
|---|---|
| AES-256-GCM | ~1 GB/s |
| RSA-2048 шифрування | ~1 MB/s |

Різниця — **~1000 разів**. Тому на практиці асиметричне та симетричне шифрування працюють **разом**: асиметричне використовується лише для початкового обміну ключами, далі — швидкий AES.

```
TLS Handshake (спрощено):

1. Server ──── Public Key ────→ Client
   (сервер надсилає свій сертифікат із публічним ключем)

2. Client ──── Encrypt(PubKey, AES_Key) ────→ Server
   (клієнт генерує випадковий AES-ключ і шифрує його
    публічним ключем сервера — лише сервер може розшифрувати)

3. Client ←── AES-GCM(AES_Key, data) ────→ Server
   (далі все спілкування через швидкий AES —
    зловмисник не знає AES_Key, бо не має приватного ключа)
```

Після handshake кожен HTTP-запит у OAuth (authorization code, token exchange, API calls) йде через цей зашифрований AES канал.

## 5. Цифрові підписи

### Навіщо підписи в OAuth

Цифровий підпис вирішує два завдання:
- **Автентичність** — хто створив дані (тільки власник приватного ключа)
- **Цілісність** — дані не були змінені після підпису

В OAuth підписи використовуються **постійно**:

| Де | Що підписується | Алгоритм |
|---|---|---|
| **JWT access token** | Claims (iss, sub, exp...) | RS256, ES256 |
| **JWT ID token (OIDC)** | Інформація про користувача | RS256, ES256 |
| **TLS сертифікат** | Публічний ключ сервера | RSA, ECDSA |
| **JWKS** | Публікація ключів для верифікації | — |

### Як працює підпис — крок за кроком

Розглянемо конкретний приклад. Authorization Server створює JWT access token для Максима:

```
Крок 1: Формуємо header + payload

Header:  {"alg":"RS256","kid":"auth-server-key-1"}
Payload: {"sub":"maksym","scope":"notes:read","exp":1700000000}

Крок 2: Кодуємо в base64url

eyJhbGciOiJSUzI1NiIsImtpZCI6ImF1dGgtc2VydmVyLWtleS0xIn0
.
eyJzdWIiOiJtYWtzeW0iLCJzY29wZSI6Im5vdGVzOnJlYWQiLCJleHAiOjE3MDAwMDAwMDB9

Крок 3: Підписуємо приватним ключем

signature = Sign(PrivateKey, header_b64 + "." + payload_b64)

Крок 4: Збираємо JWT

header_b64.payload_b64.signature_b64
```

Resource Server отримує цей JWT і перевіряє:

```
1. Декодує header → бачить "kid":"auth-server-key-1"
2. Завантажує публічний ключ з JWKS endpoint AS
3. Verify(PublicKey, header.payload, signature) → ✓
4. Перевіряє claims: exp не минув? scope підходить?
5. Надає доступ до ресурсу
```

**Ключова властивість:** Resource Server **не потребує приватного ключа** Authorization Server. Він лише перевіряє підпис публічним ключем. Це дозволяє десяткам мікросервісів перевіряти токени незалежно від AS.

### Підпис vs шифрування — різні цілі

Студенти часто плутають підпис і шифрування. Це різні операції:

```
Шифрування (Encrypt):     Підпис (Sign):
  Ціль: конфіденційність    Ціль: автентичність + цілісність
  Public key → зашифрувати  Private key → підписати
  Private key → розшифрувати  Public key → перевірити
  Хто шифрує: відправник    Хто підписує: автор
  Хто розшифровує: отримувач  Хто перевіряє: будь-хто
```

У JWT використовуються саме **підписи** (не шифрування) — payload залишається видимим, але гарантовано незмінним.

## 6. TLS — як це працює разом

### Чому TLS критичний для OAuth

**TLS** (Transport Layer Security) — протокол, який шифрує канал між клієнтом і сервером. OAuth 2.0 **вимагає** TLS (RFC 6749, Section 1.6). Без TLS весь OAuth-flow — authorization code, tokens, credentials — летить відкритим текстом.

### TLS 1.3 Handshake (спрощено)

```
Client                                    Server
  │                                          │
  │──── ClientHello (підтримувані алгоритми) ──→│
  │                                          │
  │←── ServerHello + Certificate + PublicKey ──│
  │                                          │
  │  [Перевірка сертифіката: чи підписаний   │
  │   довіреним CA? Чи не expired?]          │
  │                                          │
  │──── Key Exchange (ECDH) ────────────────→│
  │                                          │
  │  [Обидві сторони обчислюють спільний     │
  │   симетричний ключ через Diffie-Hellman] │
  │                                          │
  │←────── AES-GCM encrypted data ──────────→│
  │  [Все подальше спілкування зашифроване]  │
```

### Що відбувається при реальному OAuth-запиті

Коли Максим натискає «Увійти через Google», його браузер виконує TLS handshake із `accounts.google.com`. Можна побачити це в реальності:

```bash
$ openssl s_client -connect accounts.google.com:443 -brief
CONNECTION ESTABLISHED
Protocol version: TLSv1.3
Ciphersuite: TLS_AES_256_GCM_SHA384
Peer certificate: CN=*.google.com
...
Verification: OK
```

Це означає:
- **TLSv1.3** — найновіша версія протоколу
- **TLS_AES_256_GCM_SHA384** — 256-бітний AES у режимі GCM (те, що ми розглянули в розділі 3)
- **CN=\*.google.com** — сертифікат належить Google
- **Verification: OK** — ланцюжок довіри перевірений

Після цього **кожен** HTTP-запит OAuth-flow (redirect, token exchange, API call) летить усередині зашифрованого TLS-каналу.

### Сертифікати та PKI

Як клієнт знає, що сервер — справжній? Через **сертифікати** та **PKI** (Public Key Infrastructure):

```
Root CA (вбудований у браузер/ОС)
  │
  └── Intermediate CA
        │
        └── Сертифікат сервера (accounts.google.com)
              │
              └── Містить публічний ключ сервера
                  + підпис від Intermediate CA
```

Браузер перевіряє **ланцюжок довіри** (certificate chain): сертифікат сервера → Intermediate CA → Root CA. Якщо ланцюжок валідний — з'єднання довірене.

Для OAuth це означає: коли ваш Client робить запит до Authorization Server, TLS гарантує, що це справжній Google/GitHub/etc., а не фішинговий сайт.

### Що буде, якщо сертифікат невалідний?

```bash
$ curl https://expired.badssl.com/
curl: (60) SSL certificate problem: certificate has expired

$ curl https://self-signed.badssl.com/
curl: (60) SSL certificate problem: self-signed certificate
```

Браузер (і curl) **відмовляються** встановлювати з'єднання. Це захищає від MITM-атак (Man-in-the-Middle): зловмисник не може підставити свій сертифікат, бо він не підписаний довіреним CA.

## 7. Де шифрування зустрічається в OAuth

### Карта шифрування в OAuth-системі

```
┌─────────────────────────────────────────────────────────┐
│                OAuth 2.0 Security Layers                │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  Транспорт (TLS):                                      │
│    • AES-GCM — шифрування каналу                       │
│    • ECDH — обмін ключами                              │
│    • Сертифікат — автентичність сервера                 │
│                                                         │
│  Токени (JWT):                                          │
│    • RS256/ES256 — підпис (JWS)                        │
│      → Authorization Server підписує                    │
│      → Resource Server перевіряє                        │
│    • RSA-OAEP + AES — шифрування (JWE, опціонально)    │
│      → коли payload містить sensitive data              │
│                                                         │
│  Зберігання:                                            │
│    • AES-GCM — шифрування даних at rest                │
│      → паролі (Argon2), токени, sensitive config        │
│    • bcrypt/Argon2 — хешування паролів (Лекція 2)      │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### JWS vs JWE — підпис vs шифрування токенів

| | JWS (підписаний JWT) | JWE (зашифрований JWT) |
|---|---|---|
| Конфіденційність | **ні** — payload видимий (base64) | **так** — payload зашифрований |
| Цілісність | **так** — підпис захищає | **так** — автентифіковане шифрування |
| Типове використання | access token, ID token | токени з sensitive claims |
| Алгоритми | RS256, ES256, HS256 | RSA-OAEP + A256GCM |

**Важливо:** стандартний JWT (JWS) — **не зашифрований**. Payload закодований у base64url і будь-хто може його прочитати. Підпис лише гарантує, що payload не змінено. Не кладіть у JWT sensitive data (паролі, номери карток) без JWE.

### Приклад: JWT який може прочитати кожен

Візьмемо реальний JWT access token:

```
eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiJtYWtzeW0iLCJzY29wZSI6Im5vdGVzOnJlYWQifQ.signature...
```

Декодуємо payload (це звичайний base64url, не шифрування!):

```bash
$ echo "eyJzdWIiOiJtYWtzeW0iLCJzY29wZSI6Im5vdGVzOnJlYWQifQ" | base64 -d
{"sub":"maksym","scope":"notes:read"}
```

Будь-хто, хто перехопив цей токен (навіть без ключа), бачить, що це токен Максима з правом `notes:read`. Тому:
- **Не кладіть паролі, номери карток, персональні дані в JWT payload**
- Якщо потрібна конфіденційність claims — використовуйте JWE
- Для більшості OAuth-сценаріїв JWS достатньо, бо канал вже захищений TLS

## 8. Практика — Python приклади

### AES-GCM: шифрування нотатки в SecureNotes

```python
import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

# Генеруємо ключ (зберігати безпечно!)
key = AESGCM.generate_key(bit_length=256)
aesgcm = AESGCM(key)

# Шифруємо
nonce = os.urandom(12)  # 12 байтів, унікальний!
plaintext = "Секретна нотатка Максима".encode('utf-8')
ciphertext = aesgcm.encrypt(nonce, plaintext, None)

# Розшифровуємо
decrypted = aesgcm.decrypt(nonce, ciphertext, None)
print(decrypted.decode('utf-8'))  # Секретна нотатка Максима
```

### RSA: підпис (як у JWT RS256)

```python
from cryptography.hazmat.primitives.asymmetric import rsa, padding
from cryptography.hazmat.primitives import hashes

# Генеруємо пару ключів
private_key = rsa.generate_private_key(
    public_exponent=65537, key_size=2048
)
public_key = private_key.public_key()

# Підписуємо (Authorization Server)
message = b'{"sub":"maksym","scope":"notes:read"}'
signature = private_key.sign(
    message,
    padding.PSS(mgf=padding.MGF1(hashes.SHA256()),
                salt_length=padding.PSS.MAX_LENGTH),
    hashes.SHA256()
)

# Перевіряємо (Resource Server — має лише public key)
public_key.verify(
    signature, message,
    padding.PSS(mgf=padding.MGF1(hashes.SHA256()),
                salt_length=padding.PSS.MAX_LENGTH),
    hashes.SHA256()
)
print("Підпис валідний!")
```

## 9. Підсумки

### Що ми розглянули

- Навіщо шифрування в контексті OAuth — захист каналу, токенів, даних
- AES-GCM — симетричне шифрування (один ключ, швидке, для даних)
- RSA/ECDSA — асиметричне шифрування (пара ключів, для підписів та обміну ключами)
- TLS — поєднує обидва підходи для захисту каналу
- Цифрові підписи — основа JWT токенів
- JWS vs JWE — підпис vs шифрування токенів

### Ключові висновки

1. OAuth **вимагає TLS** — без нього всі токени летять відкритим текстом
2. **JWT підписаний, але не зашифрований** — payload видимий кожному (base64url)
3. **AES-GCM** — сучасний стандарт симетричного шифрування (шифрування + автентифікація)
4. **RSA/ECDSA підписи** — Authorization Server підписує, Resource Server перевіряє за публічним ключем
5. **Гібридне шифрування** — TLS використовує асиметричне для обміну ключами, потім симетричне для даних

### Що далі?

У наступній лекції ми переходимо до самого OAuth — **Лекція 4: OAuth 2.0 — архітектура протоколу**.

Тепер ми маємо всі криптографічні будівельні блоки:
- Лекція 2: хешування (цілісність, паролі)
- Лекція 3: шифрування та підписи (конфіденційність, автентичність)

З цими інструментами ми готові розібратися, як OAuth використовує їх для безпечного делегування доступу.
