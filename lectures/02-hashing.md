## 1. Що таке хеш-функція і навіщо вона потрібна

### Мотивація

Ви завантажили файл з інтернету — як переконатися, що його ніхто не підмінив?

У першій лекції ми розглянули **CIA Triad** — три стовпи інформаційної безпеки: конфіденційність, цілісність, доступність. Хеш-функції — це основний інструмент, який забезпечує **цілісність** (Integrity). Саме завдяки хешуванню ми можемо переконатися, що дані не були змінені або підроблені під час передачі чи зберігання.

### Визначення

**Хеш-функція** (hash function) — це детермінована функція, яка перетворює вхідні дані довільного розміру у вихідне значення фіксованого розміру. Результат називають **хешем** (hash), **дайджестом** (digest) або **відбитком** (fingerprint).

### Ключові властивості

- **Детермінованість** — однаковий вхід завжди дає однаковий вихід. Якщо ви хешуєте один і той самий файл мільйон разів — результат буде ідентичним
- **Фіксований розмір** — незалежно від розміру вхідних даних (1 байт чи 1 терабайт), вихід має однакову довжину
- **Односпрямованість** (one-way) — неможливо відновити вхідні дані з хешу. Маючи хеш, ви не зможете обчислити, які саме дані його породили
- **Лавинний ефект** (avalanche effect) — зміна одного біта входу змінює приблизно 50% бітів виходу. Навіть мінімальна зміна вхідних даних призводить до повністю іншого хешу
- **Стійкість до колізій** (collision resistance) — практично неможливо знайти два різних входи з однаковим хешем. Теоретично колізії існують (бо множина входів нескінченна, а множина виходів — ні), але знайти їх має бути обчислювально нездійсненно

### Лавинний ефект на практиці

Подивимось, як зміна лише одного символу — великої літери на малу — повністю змінює хеш:

```bash
echo -n "Hello" | sha256sum
→ 185f8db32271fe25f561a6fc938b2e264306ec304eda518007d1764826381969

echo -n "hello" | sha256sum
→ 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
```

Зверніть увагу: одна велика літера `H` замість малої `h` — і результат **повністю інший**. Жодного спільного фрагмента. Саме це і є лавинний ефект — неможливо передбачити, як зміниться хеш, маючи лише знання про зміну входу.

## 2. SHA-256 — перший інструмент

### Що означає назва

**SHA** = Secure Hash Algorithm, **256** = розмір виходу в бітах (32 байти, 64 шістнадцяткових символи). SHA-256 належить до сімейства **SHA-2**, розробленого Агенцією національної безпеки США (NSA) та опублікованого Національним інститутом стандартів і технологій (NIST) у 2001 році.

### Інтуїція

Уявіть SHA-256 як **цифровий відбиток пальця** (digital fingerprint) для будь-яких даних. Як відбиток пальця однозначно ідентифікує людину, так SHA-256 хеш однозначно ідентифікує блок даних. Два різних файли — два різних «відбитки». Якщо хоча б один біт файлу змінився — «відбиток» буде повністю іншим.

### Практичне застосування

SHA-256 використовується скрізь, де потрібна перевірка цілісності або унікальна ідентифікація даних:

- **Перевірка цілісності файлів** (checksums) — після завантаження файлу ви обчислюєте його хеш і порівнюєте з опублікованим на сайті: `sha256sum file.zip`
- **Git commit hashes** — кожен коміт у Git ідентифікується SHA-1 хешем вмісту (Git поступово переходить на SHA-256)
- **Blockchain** — у Bitcoin майнінг блоку — це пошук такого nonce, щоб SHA-256 хеш блоку починався з певної кількості нулів
- **Цифрові підписи** (digital signatures) — підписується не весь документ, а лише його хеш, що значно ефективніше

### Приклад на Python

```python
import hashlib

data = "Захист інформації"
hash_value = hashlib.sha256(data.encode('utf-8')).hexdigest()
print(hash_value)
```

### Як працює SHA-256 — загальна схема

```
┌────────────────┐     ┌──────────────┐     ┌────────────────────┐
│ Вхідні дані    │────→│  SHA-256     │────→│ 256-бітний хеш     │
│ (будь-який     │     │  hash()      │     │ (64 hex символи)   │
│  розмір)       │     └──────────────┘     │ e3b0c44298fc...    │
└────────────────┘           ↑               └────────────────────┘
                             │
                         Одностороння
                         функція — назад
                         неможливо!
```

### Перехід до наступної теми

SHA-256 чудово підходить для перевірки цілісності файлів. А що, якщо використати його для зберігання паролів?

## 3. Проблема — як зламати хеші паролів

### Сценарій: витік бази даних

Максим Витребенько працює в компанії, яка зберігає паролі користувачів як SHA-256 хеші. Здавалося б, все зроблено правильно — паролі не зберігаються у відкритому вигляді. Але одного дня базу даних зламали. Що бачить атакуючий?

| Користувач | SHA-256 хеш пароля |
|---|---|
| maksym.vytrebenko | `5e884898da28047151d0e56f8dc6292773603d0d6aabbdd62a11ef721d1542d8` |
| olena.koval | `ef92b778bafe771e89245b89ecbc08a44a4e166c06659911881f383d4473e94f` |
| admin | `8c6976e5b5410415bde908bd4dee15dfb167a9c873fc4bb8a81f6f2ab448a918` |

Атакуючий не бачить самих паролів — лише хеші. Але чи означає це, що паролі у безпеці? На жаль, ні. Розглянемо, які інструменти є в арсеналі зловмисника.

### Brute force атака (повний перебір)

SHA-256 була спроєктована як **швидка** хеш-функція — і саме це стає проблемою. Сучасне обладнання здатне обчислювати мільярди хешів на секунду:

| Пристрій | Швидкість SHA-256 |
|---|---|
| CPU (сучасний) | ~50 млн хешів/сек |
| GPU (NVIDIA RTX 4090) | ~10 млрд хешів/сек |
| Спеціалізований ASIC | ~100+ млрд хешів/сек |

Проведемо простий розрахунок. Пароль із 6 малих латинських літер — це 26^6 ≈ 309 мільйонів можливих комбінацій. При швидкості 10 мільярдів хешів на секунду (GPU) повний перебір займе:

```
309,000,000 / 10,000,000,000 = 0.03 секунди
```

**0.03 секунди** — менше ніж моргнути оком. Шестисимвольний пароль з малих літер зламується миттєво.

### Атака за словником (dictionary attack)

Атакуючі не починають із випадкових комбінацій — вони значно розумніші за це. Першим кроком завжди є **атака за словником** (dictionary attack). Зловмисник бере список найпоширеніших паролів — таких як `password`, `123456`, `qwerty`, `admin` — і обчислює SHA-256 хеш кожного з них. Потім порівнює результати з хешами із вкраденої бази.

Списки найпоширеніших паролів легко доступні в інтернеті. Наприклад, відомий список `rockyou.txt` містить понад 14 мільйонів реальних паролів, що витекли з різних сервісів. При швидкості GPU у 10 мільярдів хешів на секунду, перевірка всього словника займає частки секунди.

Саме тому паролі на кшталт `password`, `password123` та `admin` — це фактично відсутність пароля.

### Веселкові таблиці (rainbow tables)

**Веселкові таблиці** (rainbow tables) — це попередньо обчислені таблиці, які зіставляють хеш із паролем. Замість того, щоб обчислювати хеші на льоту, атакуючий завантажує готову таблицю з мільярдами заздалегідь розрахованих пар «пароль → хеш» і просто шукає потрібний хеш.

Наприклад, хеш `5e884898da28047151d0e56f8dc6292773603d0d6aabbdd62a11ef721d1542d8` миттєво розпізнається як `password`, бо він присутній у кожній веселковій таблиці. Пошук за таблицею — це, по суті, одна операція пошуку в базі даних замість мільярдів обчислень.

### Чому SHA-256 не підходить для паролів

SHA-256 — це хеш-функція **загального призначення** (general-purpose hash function), яка була спроєктована бути швидкою. Швидкість — це перевага, коли потрібно обчислити контрольну суму файлу або перевірити цілісність даних. Але для зберігання паролів швидкість стає **вразливістю**. Чим швидше обчислюється хеш, тим швидше атакуючий перебирає паролі. Нам потрібен інший підхід — і ми розглянемо його в наступних розділах.

## 4. Сіль (Salt) — перший захист

### Визначення

**Сіль** (salt) — це випадкове значення, яке додається до пароля перед хешуванням: `hash(salt + password)`. Кожен користувач отримує свою унікальну сіль, тому навіть однакові паролі породжують різні хеші.

### Як сіль змінює результат

```
Без солі:
"password123" ──→ SHA-256 ──→ ef92b778bafe...
"password123" ──→ SHA-256 ──→ ef92b778bafe...  ← ОДНАКОВІ!

З сіллю:
"a1b2c3" + "password123" ──→ SHA-256 ──→ 7c4f8a91d3e2...
"x9y8z7" + "password123" ──→ SHA-256 ──→ 1f3e5d7c9b0a...  ← РІЗНІ!
```

Два користувачі обрали однаковий пароль `password123`, але завдяки різним солям їхні хеші повністю відрізняються. Атакуючий, дивлячись на базу, навіть не зможе визначити, що паролі однакові.

### Чому сіль перемагає веселкові таблиці

Без солі атакуючий будує одну веселкову таблицю і шукає в ній усі хеші з бази. З сіллю кожен хеш обчислений з унікальною сіллю, тому атакуючому потрібна **окрема веселкова таблиця для кожної унікальної солі** — а це практично нездійсненно. Якщо в базі 10 000 користувачів із різними солями, потрібно 10 000 окремих таблиць.

### Як зберігається сіль

Сіль зберігається в базі даних **поруч із хешем**. Сіль — це **не секрет**. Її єдине завдання — бути **унікальною для кожного користувача**. Навіть якщо атакуючий бачить сіль, він не зможе використати попередньо обчислені таблиці.

| Користувач | Сіль | Хеш |
|---|---|---|
| maksym.vytrebenko | `a1b2c3d4` | `7c4f8a91...` |
| olena.koval | `e5f6g7h8` | `2d3e4f5a...` |

### Чому самої солі недостатньо

Сіль вирішує проблему веселкових таблиць, але **не вирішує проблему швидкості**. SHA-256 залишається блискавично швидкою функцією. Навіть з унікальними солями атакуючий може перебирати кожен хеш окремо зі швидкістю мільярдів обчислень на секунду. Сіль зупиняє веселкові таблиці, але не зупиняє brute force. Нам потрібно щось повільніше.

## 5. bcrypt та Argon2 — повільне хешування

### Ідея: розтягування ключа (key stretching)

Проблема зрозуміла: нам потрібна хеш-функція, яка **навмисно повільна**. Достатньо повільна, щоб brute force став непрактичним, але достатньо швидка, щоб один вхід користувача не займав хвилини. Цей підхід називається **розтягування ключа** (key stretching) — хеш-функція виконує тисячі або мільйони внутрішніх ітерацій, щоб кожне обчислення займало відчутний час.

### bcrypt (1999)

**bcrypt** — алгоритм хешування паролів, створений у 1999 році на основі шифру Blowfish. Ключова ідея bcrypt — параметр **cost factor** (фактор вартості), який контролює кількість ітерацій і, відповідно, швидкість обчислення.

Cost factor = 12 означає 2^12 = 4 096 ітерацій. Збільшення cost factor на 1 подвоює час обчислення.

bcrypt має **вбудовану генерацію солі** — вам не потрібно окремо створювати та зберігати сіль. Все зберігається в одному рядку.

Формат виходу bcrypt:

```
$2b$12$LJ3m4ys3Lg7E90WYOF3O2u8VYClVxcBqRKqhW8MiNAJG6SAPO2nJy
 ^^^  ^^  ^^^^^^^^^^^^^^^^^^^^^^  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  │    │          │                          │
  │    │          │                          └── хеш
  │    │          └── сіль (22 символи, base64)
  │    └── cost factor
  └── версія алгоритму ($2b$)
```

Приклад на Python:

```python
import bcrypt

password = "supersecret".encode('utf-8')
salt = bcrypt.gensalt(rounds=12)
hashed = bcrypt.hashpw(password, salt)

# Перевірка
bcrypt.checkpw(password, hashed)  # True
```

Вплив cost factor на час обчислення:

| Cost factor | Ітерацій | Час хешування |
|---|---|---|
| 10 | 1 024 | ~100 мс |
| 12 | 4 096 | ~300 мс |
| 14 | 16 384 | ~1 сек |

При cost factor = 12 одне хешування займає ~300 мс — цілком прийнятно для логіну, але катастрофічно для brute force. Якщо атакуючий раніше перебирав 10 мільярдів SHA-256 хешів на секунду, то з bcrypt він зможе перебрати лише ~3 хеші на секунду.

### Argon2 (2015)

**Argon2** — переможець конкурсу Password Hashing Competition (2015), сучасний стандарт хешування паролів. Головна перевага Argon2 над bcrypt — він контролює не тільки час, а й **пам'ять**.

Argon2 має три виміри складності:

- **Час** (time cost) — кількість ітерацій, аналогічно до cost factor у bcrypt
- **Пам'ять** (memory cost) — скільки RAM потрібно для обчислення одного хешу
- **Паралелізм** (parallelism) — кількість потоків, що використовуються

Чому **стійкість до пам'яті** (memory-hardness) має значення? GPU мають тисячі ядер, але обмежений об'єм пам'яті на кожне ядро. Якщо кожне обчислення хешу потребує 64 МБ RAM, то GPU з 10 000 ядрами потребуватиме 640 ГБ лише для паралельного хешування — це непрактично.

```
bcrypt:                         Argon2:
┌──────────┐                    ┌──────────┐
│ Повільний │                    │ Повільний │
│ по часу   │                    │ по часу   │
│           │                    │ + багато  │
│           │                    │   RAM     │
│           │                    │ + потоки  │
└──────────┘                    └──────────┘
GPU: може паралелити          GPU: не вистачає
     тисячі обчислень               пам'яті на ядро
```

Argon2 має три варіанти:

- **Argon2d** — data-dependent, оптимізований для стійкості до GPU, але вразливий до атак по сторонніх каналах
- **Argon2i** — data-independent, стійкий до атак по сторонніх каналах, але менш ефективний проти GPU
- **Argon2id** — гібрид, поєднує переваги обох. **Рекомендований варіант** для хешування паролів

Приклад на Python:

```python
from argon2 import PasswordHasher

ph = PasswordHasher(time_cost=3, memory_cost=65536, parallelism=4)
hash = ph.hash("supersecret")

ph.verify(hash, "supersecret")  # True
```

### Порівняння алгоритмів

| | SHA-256 | bcrypt | Argon2 |
|---|---|---|---|
| Призначення | загальне хешування | хешування паролів | хешування паролів |
| Швидкість | дуже швидкий | повільний (налаштовується) | повільний (налаштовується) |
| Вбудована сіль | ні | так | так |
| Memory-hard | ні | ні | **так** |
| GPU-стійкість | ні | частково | **так** |
| Рекомендація | файли, підписи | паролі (legacy) | **паролі (сучасний стандарт)** |

## 6. CSPRNG — звідки береться випадковість

bcrypt та Argon2 генерують сіль автоматично. Але що робить сіль якісною? Вона має бути **непередбачуваною**. Якщо атакуючий може вгадати або відтворити сіль, веселкові таблиці знову стають ефективними. Тому спосіб генерації випадкових значень — це питання безпеки, а не зручності.

### PRNG vs CSPRNG

Не всі генератори випадкових чисел однакові. Існують два принципово різних підходи:

- **PRNG** (Pseudo-Random Number Generator) — генератор псевдовипадкових чисел. Приклад: `random.randint()` у Python. PRNG є детермінованим — знаючи початкове значення (seed), можна відтворити всю послідовність. Це швидко і достатньо для ігор, симуляцій та статистичних експериментів, але **непридатно для безпеки**
- **CSPRNG** (Cryptographically Secure PRNG) — криптографічно безпечний генератор псевдовипадкових чисел. Приклад: `os.urandom()`, `secrets.token_hex()` у Python. CSPRNG гарантує, що навіть знаючи всі попередні згенеровані значення, **неможливо передбачити наступне**

Чому PRNG небезпечний для криптографії? Якщо атакуючий дізнається або вгадає seed (а seed часто базується на поточному часі), він зможе відтворити всі «випадкові» значення — солі, токени, ключі. У цьому випадку веселкові таблиці знову стають ефективними, бо атакуючий може передбачити сіль кожного користувача.

### Звідки береться ентропія

CSPRNG потребує джерела справжньої випадковості — **ентропії** (entropy). Звідки операційна система її отримує?

- **Апаратні події** (hardware events) — рух миші, інтервали між натисканнями клавіш, час операцій читання/запису диска, час прибуття мережевих пакетів. Ці події мають мікроскопічну непередбачуваність, яку система накопичує
- **Пул ентропії ОС** (OS entropy pool) — операційна система збирає ентропію з апаратних подій у спеціальний пул. У Linux та macOS це `/dev/urandom`, у Windows — `CryptGenRandom`
- **Апаратний генератор випадкових чисел** (hardware RNG) — сучасні процесори мають вбудовані генератори. Наприклад, інструкція Intel `RDRAND` генерує випадкові числа на основі фізичних процесів у кристалі

### Практичні правила

Для генерації паролів, токенів, солей та ключів:

- **Python:** `secrets.token_hex(32)`
- **Bash:** `openssl rand -hex 32`

**НІКОЛИ** не використовуйте для криптографічних цілей:

- `random.random()` (Python)
- `Math.random()` (JavaScript)
- `rand()` (C/PHP)

Ці функції — PRNG, вони передбачувані і не призначені для безпеки.

### Приклад на Python

```python
import secrets
import random

# ПРАВИЛЬНО — для токенів, солей, ключів:
token = secrets.token_hex(32)

# НЕПРАВИЛЬНО — передбачуваний, НЕ для безпеки:
bad_token = ''.join(str(random.randint(0,9)) for _ in range(32))
```

## 7. Підсумки

### Що ми розглянули

- Хеш-функції та їх ключові властивості (детермінованість, фіксований розмір, односпрямованість, лавинний ефект, стійкість до колізій)
- SHA-256 — швидке хешування для цілісності даних
- Атаки на хеші паролів — brute force та rainbow tables
- Сіль — захист від rainbow tables
- bcrypt та Argon2 — повільне хешування для паролів
- CSPRNG — криптографічно безпечна генерація випадкових значень

### Ключові висновки

1. Хеш-функція — це «цифровий відбиток» даних: одностороння, детермінована, з лавинним ефектом
2. SHA-256 підходить для перевірки цілісності, але **занадто швидкий** для зберігання паролів
3. Сіль захищає від rainbow tables, але не від brute force — потрібне **повільне хешування**
4. **Argon2id** — сучасний стандарт хешування паролів (memory-hard, GPU-стійкий)
5. Для будь-яких криптографічних цілей використовуйте лише **CSPRNG** — ніколи `random()`

### Що далі?

У наступній лекції ми розглянемо **симетричне шифрування** — Лекція 3: Симетричне шифрування. AES (CBC, GCM).

Хешування — це одностороння функція: дані «в одну сторону». Але що, якщо нам потрібно **зашифрувати** дані так, щоб їх можна було **розшифрувати** назад?

- **AES** (Advanced Encryption Standard) — симетричний блоковий шифр, стандарт шифрування
- Режими шифрування: **CBC** (Cipher Block Chaining) — ланцюгування блоків шифротексту, та **GCM** (Galois/Counter Mode) — режим лічильника з автентифікацією Галуа
- Ключі, вектори ініціалізації (**IV** — Initialization Vector) та padding

Ці примітиви дозволяють нам захистити конфіденційність даних — другий стовп CIA Triad.
